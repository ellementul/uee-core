## Транспорт: архитектура хоста и клиента

Транспорт всегда состоит из двух частей: **хоста** и **клиента**.

### Принципы подключения

- **Хост** может быть инструментом, но для прозрачности архитектуры подключается только к участнику-комнате: требует инструмент комнаты как зависимость и через него добавляет себя в комнату как виртуального участника. Это также экономит на правах доступа.
- **Клиентская часть** не зависит от инструмента комнаты: она имитирует виртуальную внешнюю комнату, в которую участник вступает. Участнику кажется, что он подключён к другому участнику, а на самом деле — к транспорту.

### Уровень инструмента

1. Имитация подключения к комнате.
2. Имитация работы комнаты или участника.
3. Управление соединениями:
   1. создание фабрики соединений;
   2. управление соединениями:
      - получение нового соединения;
      - механизм бесшовной подмены соединения;
      - механизм сравнения соединений: связывают одни и те же две точки; учитывают стабильность и скорость;
      - преобразование действий с соединениями в события, на которые можно подписаться; эти события **не ходят** по самому соединению на другую сторону.
4. Для хоста:
   - получать подписки и отписки через соединения, подключая коллбэки отправки сообщений соединений к реальным подпискам;
   - оборачивать каждый коллбэк отправки в кэширование, отсекая повторяющиеся сообщения (функциональность дублируется, потому что хост — не настоящий участник, а его имитация);
   - получать сообщения от клиента и передавать их в комнату выше как обычный участник.
5. Для клиента:
   - имитировать работу провайдера — возможно, достаточно синхронного `Provider`;
   - хранить список подписок;
   - отправлять подписки сообщениями по транспорту, если соединение создано или перезагружено;
   - прекращать отправку подписок только когда все они подтверждены другой стороной; список подтверждённых прикреплён к соединению и сбрасывается вместе с ним;
   - полученные сообщения передавать как обычные события, по возможности через готовый `Provider`.

### Уровень фабрики соединений

- Фабрика обязана соответствовать заранее заданному интерфейсу.
- Для хоста фабрика принимает конфиг через конструктор.
- Для клиента конфиг передаётся вторым аргументом `onConnection`. **Противоречие в исходном доке:** в коде-наброске у `ClientConnectionFactory` также есть `constructor(config)` и `onConnection(callback)`. Нужно решить, что является каноничным: базовый конфиг в конструкторе + переопределение в `onConnection`, или только второй аргумент.

```js
class HostConnectionFactory {
  constructor(config) { /* ... */ }

  // Первый вызов запускает фабрику; повторный заменяет callback
  // и передаёт ему все существующие соединения
  onConnection(callback) { /* ... */ }

  // Остановка фабрики, закрытие всех соединений
  stop() { /* ... */ }

  // Единая воронка для ошибок сети и соединений
  onError(callback) { /* ... */ }
}

class ClientConnectionFactory {
  constructor(config) { /* ... */ }

  // Первый вызов создаёт соединение; повторные возвращают новое
  // соединение в callback, старое не удаляется
  onConnection(callback, config) { /* ... */ }

  stop() { /* ... */ }
  onError(callback) { /* ... */ }
}
```

### Уровень соединения

```js
class Connection {

  onMessage(callback) { /* ... */ }
  close() { /* ... */ }
  onClose(callback) { /* ... */ }
  onError(callback) { /* ... */ }
}
```

### Middleware

Обёртка поверх соединения, которая точно имитирует его интерфейс до оборачивания. Не имеет собственного способа передать данные наружу кроме интерфейса соединения: «чистая событийность», но с возможностью работать с сообщениями до их обработки как событий.
